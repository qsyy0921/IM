# Hot Group Runtime Profile Bottleneck Check

Generated by Backend Lab on 2026-07-02.

Scope: diagnostic only. These runs are not production capacity claims.

## Why This Check Was Run

The previous policy-facts run showed:

- `message_repository_pool_acquire_recent` p99 around `252.653ms`;
- `policy_decision_audit_outbox` p99 around `113ms`;
- PostgreSQL was the hottest backend container, while Go service CPU remained low.

Before changing business logic again, Backend Lab checked whether the Ubuntu
runtime profile matched the intended loadtest profile.

## Runtime Drift Found

Ubuntu `nexusim-message-service-grpc` did not have `NEXUSIM_PG_MAX_CONNS` set.
The service therefore used pgx default pool sizing, which was `72` on that host,
not the intended local loadtest default of `192`.

Ubuntu PostgreSQL was also running only the base compose command:

- `shared_buffers=128MB`
- `max_wal_size=1GB`
- `checkpoint_timeout=5min`

Backend Lab synced the local compose runtime profile to Ubuntu and recreated the
runtime:

- message-service PG pool: `192`
- PostgreSQL `shared_buffers=1GB`
- PostgreSQL `max_wal_size=4GB`
- PostgreSQL `checkpoint_timeout=15min`

After the experiments, policy-service was restored to the default audit pool of
`32`; message-service remains on pool `192`, and PostgreSQL remains on the
loadtest profile.

## Evidence

With `message-service` pool corrected to `192`, the old message pool wait mostly
disappeared:

- previous final run: `message_repository_pool_acquire_recent` p99
  `252.653ms`;
- runtime-profile run: `message_repository_pool_acquire_recent` p99
  `5.067ms`;
- audit64 diagnostic: `message_repository_pool_acquire_recent` p99
  `22.178ms`.

That means the earlier message pool wait was a real runtime-profile problem,
not the final logical bottleneck.

After removing that local message pool queue, pressure moved to shared
PostgreSQL write paths:

- audit32 runtime-profile run:
  - `policy_decision_audit_outbox` p99 `265ms`;
  - policy audit PG pool empty acquires `4817`;
  - policy audit PG acquire duration total `928158ms`;
  - delivery outbox did not drain inside the runner wait window.
- audit64 diagnostic:
  - `policy_decision_audit_outbox` p99 `289ms`;
  - message outbox was still pending `3404` at the timeout point;
  - delivery timeline projection only reached `1596/5000`;
  - increasing audit pool improved SendMessage p99 versus audit32, but pushed
    more pressure into message outbox relay / delivery projection.

Resource sampling used pressure-related processes/containers only and stopped
30 seconds after the runner:

- audit32 runtime-profile run:
  - PostgreSQL avg/max CPU `192.122% / 3933.66%`;
  - message-service avg/max CPU `20.218% / 1000.78%`;
  - Kafka avg/max CPU `39.013% / 303.36%`.
- audit64 diagnostic:
  - PostgreSQL avg/max CPU `161.898% / 249.67%`;
  - delivery timeline consumer avg/max CPU `10.759% / 31.65%`;
  - message outbox relay avg/max CPU `5.463% / 14.37%`.

The very high one-sample CPU spikes should be read as process-sampler spikes,
not sustained capacity. The stable conclusion is the direction of pressure:
PostgreSQL is the shared hot component, and Go service CPU is not the limiting
resource.

## Current Bottleneck

The pipeline has now been narrowed to shared PostgreSQL write contention:

1. `SendMessage` synchronously waits for policy decision audit outbox insert.
2. The same request path also writes message log, timeline, and message outbox.
3. Message outbox relay, delivery projection, and delivery outbox relay then
   continue writing through PostgreSQL.
4. Raising message-service pool removes one local queue but increases pressure
   on the shared PG write path.
5. Raising policy audit pool is not a clean fix; it can improve one part of
   SendMessage latency while starving async outbox/projection work.

Not current primary bottlenecks:

- policy facts read;
- policy Redis cache;
- conversation seq allocation;
- message-service local PG pool after profile correction;
- Kafka as a standalone bottleneck;
- Go CPU saturation in message-service or policy-service.

## Next Investigation Step

Do not keep increasing PG pools blindly. The next useful change is observability
and isolation around audit / relay writes:

1. Split policy audit stage metrics into `audit_pool_acquire` and
   `audit_insert_exec`, so we can see whether the `decision_audit_outbox` p99 is
   mostly pool wait or the insert itself.
2. Ensure message outbox relay and delivery timeline/outbox worker metrics are
   scraped and included in the hotgroup metrics window. The current run proved
   async tail can become the bottleneck, but the Prometheus report did not expose
   enough relay-stage detail.
3. Test audit outbox table partitioning / index reduction / smaller payload
   before considering a separate audit PostgreSQL instance.
4. Consider separate audit PostgreSQL only after confirming audit insert is the
   dominant writer and reviewing fail-closed audit semantics.
